## 1. Overview

CityFix is a citizen-issue reporting and tracking platform for Bangladeshi city corporations, built around four roles (citizen, dispatcher, field crew, admin) sharing one ticket model. Citizens report issues from a phone or laptop; dispatchers route them to crews; field crews resolve them with photo proof; admins configure cities. The platform's value is **visibility** — making silence about civic problems visible and tracking the response.

**v1 target:** a lean, single-deployment web app that the Dhaka city corporation can run for a full pilot (estimated <50k citizens served in v1) and that the Aamir persona can replicate to new cities via the Dhaka template.

This document is the **master PRD**. It sets the cross-cutting product framing; per-WO feature PRDs (`000-platform-foundation.xml`, `001-citizen-report-flow.xml`, `002-dispatcher-queue.xml`, `003-field-crew-app.xml`, `004-admin-city-setup.xml`) hold the requirement-level detail.

## 2. Goals

From `design-artifacts/A-Product-Brief/01-product-brief.md` and `design-artifacts/B-Trigger-Map/01-business-goals.md`:

1. **Visibility** — every reported issue is visible; every status change is visible; silence is visible (Feature #2, #6, #10).
2. **Trust** — the trust loop works: a citizen files → sees acknowledgement → sees routing → sees progress → sees resolution (Features #2, #3, #9, #12).
3. **Operational clarity** — Habib and Rashid can act on the ticket queue without chaos (Features #4, #5, #8, #11).
4. **Lean city rollout** — Aamir can stand up a new city from the Dhaka template (Feature #11).
5. **Operational sustainability** — the platform runs leanly so city-corp IT can sustain it (Goal 3).

**Non-goals for v1:**
- Native mobile apps (PWA install only; native wrappers deferred)
- Multi-region failover (single region)
- Custom-role builder (Feature #18 deprioritized)
- Public adoption dashboard (deferred to v1.1)
- WebSocket push (polling 10–30s for v1)
- City-corp-wide analytics beyond ward-level performance snapshots

## 8. Acceptance criteria (cross-cutting)

These apply to the entire v1, not just WO-000.

**Functional**
- [ ] Citizens can register, verify (OTP), file a report, see status trail, receive resolution notification
- [ ] Dispatcher can see the daily queue, assign to crew, monitor, resolve-confirm
- [ ] Field crew can accept, start, capture before/after, mark resolved (offline-queue tolerant)
- [ ] Admin can create a new city from the Dhaka template, configure categories/wards/depts, provision users

**Non-functional**
- [ ] Citizen report flow: tap top-bar CTA to submit confirmation ≤ 60s on a mid-range device (Feature #1)
- [ ] Field-crew flow tolerates 3G; offline changes queue locally and retry on reconnect (Feature #4)
- [ ] Bangla-first, English-secondary; per-user toggle (Feature #13)
- [ ] Multi-photo defaults: cap = 3, narrow-category cap = 2, mandatory min = 1 (UX Review #6)
- [ ] Visual regression: all 7 hero mockups pass Playwright `npm run test:mockups` at `tolerance: 0.005`; per-WO route tests added as WOs ship

**Cross-cutting (Do Not Change)**
- **Web-first layout** + **Rashid phone-fallback** (Phase B, 2026-10-04)
- **Bangla-first, English-secondary** i18n
- **Four-role model** — no custom-role builder in v1
- **WebAuthn mandatory for admin writes**
- **Dedup is a prompt, not auto-merge** (Feature #3)
- **Internal-fields-hidden-from-citizens** schema boundary
- **Polling (10–30s) for v1**; WebSocket deferred to v1.1
- **PWA installable, not native**
- **Multi-photo defaults** (cap 3 / narrow 2 / min 1)
- **Outdoor high-contrast theme** (`.theme-outdoor`) for Rashid's in-progress page

## 9. Risks + mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Bangladesh SMS-OTP delivery is unreliable | High | High | WO-000 provides a provider abstraction; Aamir can swap providers per city; v1 has a one-time-code fallback for citizens without SMS |
| 3G bandwidth on Rashid's cracked phone | High | Medium | WO-003 offline queue; client-side image compression (1600px q80); service worker caches shell only |
| Multi-city config drift | Medium | Medium | Dhaka template pre-populates; audit log records every config change (Feature #22) |
| Privacy of citizen phone + NID | Medium | High | Argon2 password hashing; HTTP-only cookies; per-citizen push scope; internal-fields-hidden-from-citizens schema rule |
| Map tile availability in Bangladesh | Medium | Low | MapLibre + OSM in dev; Mapbox upgrade path; ward polygons served from city config |
| Aamir doesn't onboard | Low | Critical | Dhaka template auto-runs; admin UI is a 7-page walk-through, no custom config needed for v1 |
