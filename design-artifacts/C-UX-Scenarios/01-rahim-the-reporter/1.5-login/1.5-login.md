# Login (returning users)

**Route:** `/login`
**Scenario:** Rahim the Reporter — Reports a broken streetlight (screen 5 of 14)
**Purpose:** Authenticate returning Rahim and route to Home in under five seconds.

> **Phase B (2026-10-04):** Login keeps its centered single-column layout (`max-width: 480px`). The **sticky-bottom CTA** is replaced with an in-flow button at the bottom of the card. See `_progress/00-design-log.md` for the re-skin.

---

## User Context

Rahim arrives here from one of three paths:
- **First run:** taps "I already have an account" on `/welcome`
- **Returning session:** app reopens, no valid auth token, routes here automatically (Welcome is skipped via the `welcome_seen` flag)
- **Logout:** explicit logout from Settings (later page) routes here

His arrival state is **familiar and transactional**: he knows what CityFix is, has been through it before, just wants to get in. Lower friction tolerance than first-time registration because he expects speed, not patience.

## Content & Actions

### Page container

- **Page name:** `login-page`
- **Language:** Bangla default (persisted from prior session).
- **Layout:** Web-first. Single column, scrollable, centered. The card is constrained to `max-width: 480px` at all viewports, sitting on a calm neutral background. Header lives inside the column; the **Log in** button is in-flow, not sticky-bottom.

### Header

- **`login-header`** — height 56px.
- **Left:** back arrow `<`. Tap → if first-run path, returns to `/welcome`. If returning-session or logout path, closes the app (no further back).
- **Center:** CityFix wordmark.

### Title block

- **`login-title`** — H1.
  - **Bangla:** "লগ ইন করুন"
  - **English:** "Log in"
- **`login-subtitle`** — body text, optional warm acknowledgment.
  - **Bangla:** *(omitted — Bangla uses a more transactional register; "স্বাগতম" feels off)*
  - **English:** "Welcome back."
- **Decision:** subtitle shows only on the English surface. Bangla surface goes directly to the form. This honors the language-strategy decision in `content-language.md` (Bangla register is clear and capable, not warm-fluffy).

### Form

Two fields, vertical stack, 16px gap.

#### Field 1 — Phone

- **`login-input-phone`** — same spec as Registration. Country code chip "🇧🇩 +880" non-editable prefix, 11-digit Bangladeshi number input. Numeric keyboard.
- **Pre-filled from local storage** if a phone was previously logged in: `localStorage.last_phone` is read on render and shown in the field (masked? — see Open Questions). User can edit.

#### Field 2 — Password

- **`login-input-password`** — label "Password" / "পাসওয়ার্ড". Input type password (masked). Show/hide eye toggle on the right. Numeric-and-symbol keyboard. Placeholder: "••••••••".

### Primary action

- **`login-button-submit`** — **in-flow** (not sticky), full-width inside the 480px column, 56px tall. 24px of breathing room between the password field and the button.
  - **Label (BN):** "লগ ইন"
  - **Label (EN):** "Log in"
  - **State:** disabled until both fields filled. Enabled = primary brand color.

### Secondary link — forgot password

- **`login-link-forgot-password`** — text link below the password field, right-aligned.
  - **Bangla:** "পাসওয়ার্ড ভুলে গেছেন?"
  - **English:** "Forgot password?"
  - Tap → routes to `/forgot-password` (separate flow, **out of scope for this spec** — to be specified separately if/when needed for v1).

### Tertiary link — register

- **`login-link-register`** — text link centered, below the CTA, 32px above bottom safe area.
  - **Bangla:** "নতুন এখানে? নিবন্ধন করুন"
  - **English:** "New here? Register"

## Behavior

### Session validity

- On app open, the app checks `localStorage.auth_token` for validity (not expired, JWT signature valid).
- **Valid token present:** skip Login, route directly to Home.
- **No token, or token expired:** route to Login.
- This is the *implicit* "remember me" — log in once, stay logged in across sessions, until the user explicitly logs out (via Settings).

### Auto-fill

- Phone field is **pre-filled from `localStorage.last_phone`** if present. The user can edit it if they want to log in as a different account on the same device. **Default:** pre-fill, but the cursor still focuses the field so it's obvious the user can edit.
- Password field is **never** pre-filled. Always empty.

### Login flow

1. Both fields filled → tap Submit.
2. Submit button shows spinner; inputs disabled.
3. App POSTs `{phone, password}` to `/api/v1/auth/login`.
4. **On 200 OK:** JWT token stored in `localStorage.auth_token`. Phone stored in `localStorage.last_phone`. App routes to `/home`.
5. **On 401 (wrong credentials):** see Wrong Credentials state.
6. **On 423 (locked):** see Locked state.
7. **On 5xx or network failure:** toast "সংযোগ ব্যর্থ — আবার চেষ্টা করুন" — inputs re-enabled.

### Back navigation

- First-run path → back to `/welcome`.
- Returning-session path → closes app.
- Logout path → closes app.

## States

### Default

Two empty fields. Submit disabled. Forgot password link visible below password. Register link below CTA.

### Pre-filled phone (returning user)

Phone field shows previously-used number (see Open Questions on masking). Cursor is in phone field — if user just wants to type password, focus jumps to password on first keypress.

### Submitting

Submit button shows spinner. Label changes to "Logging in..." / "লগ ইন হচ্ছে..." Inputs disabled.

### Wrong credentials

Inline error below password field, in red: "ফোন নম্বর বা পাসওয়ার্ড ভুল" / "Wrong phone or password" — *deliberately vague* to avoid revealing which field is wrong. Inputs cleared (both fields reset to empty) so the user can re-enter.

### Locked (too many attempts)

After 5 wrong attempts within 10 minutes, the form is replaced with a centered message: "অনেক চেষ্টা হয়েছে — কিছুক্ষণ পর আবার চেষ্টা করুন" / "Too many attempts — try again later." Below: a "Forgot password?" link that still routes to `/forgot-password` as an alternative recovery path.

### Network failure

Toast at bottom: "সংযোগ ব্যর্থ — আবার চেষ্টা করুন" / "Connection failed — try again." Inputs re-enabled. Submit re-enabled.

## Success

Rahim taps Log in, JWT is issued, app routes to Home. He is now authenticated; the app's behavior on subsequent opens is to skip Login until he explicitly logs out.

**Emotional outcome:** Returning Rahim's experience is **invisible** — the app got him back to where he was, fast. There is no emotional residue because there should be no emotional ask. The page's success metric is **time-to-Home**, not delight.

## Open Questions

- **Phone masking on pre-fill** — if Rahim's phone is "+880 1712-345-678", should the field show it fully, masked middle ("+880 1712-\*\*\*-678"), or fully masked? **Default:** show fully if the user is on the device they last logged in on (no security boundary to enforce); mask the middle if a "this isn't me" link is added. **Decision deferred until Settings / security model is spec'd.**
- **"Forgot password" flow** — referenced from this screen but not in any of the four scenarios. **Default for v1:** ship the link, route to a placeholder page that says "Password reset coming soon. Contact support@cityfix.bd for now." Defer real flow to v2 unless the operating city corp asks for it earlier.
- **Auto-login on shared devices** — no "remember me" toggle. If the user shares the device with family, they should explicitly log out. **Default for v1:** trust the device. **Risk:** household devices where kids might see the app. **Mitigation:** deep-link from notifications should still respect auth state, so accidental disclosure is limited.
- **OTP fallback for forgotten password** — should Login have a "Log in with OTP" path (skip password, send SMS code instead)? **Default for v1:** no. Adds complexity, security surface, and SMS gateway load. Defer to v2.
