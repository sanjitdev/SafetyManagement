# Resolution Notification (push)

**Route:** deep link `cityfix://tickets/{ticket_id}` opened from a push notification
**Scenario:** Rahim the Reporter — Reports a broken streetlight (screen 14 of 14)
**Purpose:** Bring Rahim back into the app at the moment his report is resolved, with the proof right there.

> **Phase B (2026-10-04):** Notification deep-link behavior unchanged. The destination page (`/reports/{ticket_id}`) is now the re-skinned My Reports Detail (see spec 1.12). The feedback prompt is the same. The deep-link routing logic (skip Welcome / Login if JWT valid; replace current screen if mid-flow) is unchanged. See `_progress/00-design-log.md` for the re-skin.

---

## User Context

Rahim is doing something else entirely. His phone buzzes. He sees a notification from CityFix: "Your streetlight report — fixed. Tap to view." He taps. He lands directly on the resolved report with the before/after photo pair. This is the *closing of the loop*.

---

## Content & Actions

### Trigger

- Server-side: when Habib (dispatcher) confirms a resolution, the server pushes a notification to all reporters linked to the ticket (via dedup).
- Push payload: `{type: "ticket_resolved", ticket_id, category_label}`

### Notification text

- **Bangla:** "আপনার #{ticket_id} রিপোর্ট সমাধান হয়েছে — দেখুন" / "Your #{ticket_id} report is resolved — view it"
- **English:** "Your #{ticket_id} report is resolved — view it"
- Includes a small CityFix logo (TBD — icon).

### Deep-link behavior

- App is closed: tap notification → app opens, lands on `/my-reports/{ticket_id}` (My Reports Detail) directly. Welcome / Login are skipped because the JWT in local storage is still valid.
- App is backgrounded: tap notification → app foregrounds, lands on the same detail page.
- User is mid-flow (e.g., on Home): tap notification → routes to detail page, replacing the current screen.

### Page behavior

- The My Reports Detail page (see spec) renders the same content, but the **feedback prompt** is shown prominently at the top because resolution is the headline reason for this entry point.

---

## Behavior

### Notification permissions

- Requested on first authenticated open (see Home spec). If denied, this notification path is silently skipped — Rahim has to discover the fix by checking his reports himself.

### Notification grouping

- Multiple ticket_resolved notifications are grouped under the CityFix app name in the OS notification tray.

### Tapping behavior

- See Trigger / Deep-link above.

### In-app badge

- The Home notifications icon (`home-button-notifications`) shows an unread badge while there are unseen notifications.

---

## States

### Notification arrives (app closed)

Standard OS notification with the text above.

### User taps notification

Routes to `/my-reports/{ticket_id}`. Detail page renders normally with feedback prompt highlighted.

### User ignores notification

Notification stays in tray; badge on Home bell increments.

### Notifications disabled

No notification arrives; user discovers resolution by checking `/my-reports` directly.

---

## Success

Rahim's report is resolved, his phone buzzes, he taps, sees the before/after pair, taps "Yes, fixed" feedback. The loop is closed. He is now a daily user.

**Emotional outcome:** This is the single most important *conversion event* in CityFix. The first time a citizen sees their report resolved with a notification, they understand what the platform is. The next time they see something broken, they reach for CityFix without hesitation.

---

## Open Questions

- **Notification copy variations** — should the notification say which category was resolved? **Default for v1:** include category in the text ("Your streetlight report — fixed").
- **Multiple language notifications** — Bangla or English based on the user's `preferred_language`. **Default: yes.**
- **In-app banner vs. push** — should there be an in-app banner for resolution when the user is already on the app? **Default for v1: no** — avoid duplicate surfacing. Push is sufficient.
